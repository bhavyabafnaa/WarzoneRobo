# WarzoneRobo

WarzoneRobo contains research code exploring reinforcement learning (RL) techniques for navigating grid based strategy maps. The project compares vanilla policy gradients with techniques that improve exploration or planning.

Unlike a typical navigation task with a goal location, the agent's objective here is long-term survival. Each step incurs cost and risk penalties based on the current maps, so policies must balance movement with staying alive.

## Project goals
* Train an agent using Proximal Policy Optimization (PPO).
* Augment the agent with Intrinsic Curiosity Module (ICM) and Random Network Distillation (RND) to encourage exploration.
* Combine RL with a risk-aware local planner that guides policy learning through reward shaping.

## Getting started
The repository includes a Jupyter notebook named `demo.ipynb` that showcases the environment and training utilities. You can run the notebook interactively or execute its cells as a script.

```bash
# Install dependencies
pip install -r requirements.txt

# Launch Jupyter and open the notebook
jupyter notebook demo.ipynb
```

Install `requirements-logging.txt` only when using TensorBoard or Weights &
Biases. Development and CI dependencies are listed in `requirements-dev.txt`.

Alternatively, you can run the notebook from the command line using `jupyter nbconvert`:

```bash
jupyter nbconvert --to notebook --execute demo.ipynb --output output.ipynb
```

### Command line training
You can also train the models directly with `train.py`. Hyperparameters can be
supplied via command line flags or a YAML configuration file:

```bash
python train.py --grid_size 8 --num_episodes 200
```

or

```bash
python train.py --config configs/default.yaml
```
To store generated figures run with `--plot-dir`:
```bash
python train.py --config configs/default.yaml --plot-dir figures
```

The repository includes `configs/default.yaml` as a starting configuration.
Duplicate and modify this file to experiment with different training settings.
Additional environment options can also be specified in the YAML:

```yaml
grid_size: 8
num_episodes: 200
dynamic_risk: true      # enemies increase risk over time
dynamic_cost: true     # cost near mines decays and rises dynamically
add_noise: true         # perturb loaded maps on reset
```

## Results status

The pre-fix CSV/HTML tables were removed from the corrected branch and remain
recoverable in Git history. Existing checkpoints, figures and videos were
generated by the pre-validity-fix pipeline and **must not be cited**. That
pipeline collapsed
single-transition ICM rewards to zero, did not update ICM parameters with the
correct optimizer, shifted state/action pairs in the PPO buffer, mixed planner
actions into the on-policy objective, included planner shaping in reported
environment reward, and did not fully control benchmark randomness.

The corrected five-seed rerun did not establish superiority of PPO + ICM +
Planner. It produced no statistically significant advantage, and every greedy
held-out policy collapsed to the same constant action. Those findings motivate
the preregistered pure-survival protocol below; they are not evidence that the
hybrid is better. See [`RESULTS_STATUS.md`](RESULTS_STATUS.md) for the exact
validity boundary.

The definitive experiment matrix is:

| Key | Variant |
| --- | --- |
| `ppo` | PPO Only |
| `icm` | PPO + ICM |
| `rnd` | PPO + RND |
| `pc` | PPO + stable hashed pseudo-count |
| `planner` | PPO + Planner |
| `icm_planner` | PPO + ICM + Planner |

Pure-survival protocol v1 was rejected during calibration after all six
variants produced zero full-horizon survival across 22,000 training episodes.
Protocol v2 fixes the resulting observability and unsafe-action floor before
any confirmatory outcomes are collected.

The v2 confirmatory configuration uses 30 training, 10 validation, and 30 test
maps from a fresh generation-seed range. Every run rotates deterministically
across all training maps. Variants with the same run seed receive matched maps,
environment randomness, evaluation starts, and action-sampling seeds.

### Confirmatory pure-survival protocol

`configs/confirmatory.yaml` declares the experiment before results are
inspected:

* six variants, 40 matched training seeds, and 500 episodes per run;
* random starts with boundary, mine, and enemy clearance;
* policy-visible enemy locations and a common observation-derived safety mask
  that prevents every variant from intentionally entering a visible lethal
  cell;
* a survival curriculum that increases the training horizon from 20 to 100
  steps while evaluation always uses the full 100-step horizon;
* 20 stochastic rollouts per held-out map as the primary evaluation, with
  greedy evaluation reported secondarily;
* held-out survival rate as the primary outcome, defined as reaching
  `max_steps` without hitting a mine or enemy;
* PPO + ICM + Planner compared with every other variant using paired tests and
  Holm family-wise error correction; and
* a required improvement of at least 0.05 in absolute survival rate for each
  comparison, in addition to corrected statistical significance.

Before training, an automatic validity gate evaluates four constant-action
policies, raw and safety-masked random policies, four masked fixed-preference
policies, and a safe non-learning heuristic on every split. The masked controls
and heuristic are restricted to the same observation channels available to
PPO, making the contribution of the common safety shield auditable.
Constant-action survival must remain at or below 0.10 and safe-heuristic
survival must be at least 0.10. This rejects both degenerate and demonstrably
unsolvable map sets.

Before the 40-seed run, execute `configs/calibration_v2.yaml`. Every variant
must achieve at least 0.05 stochastic held-out survival or the run exits with a
failed calibration decision:

```bash
python train.py --config configs/calibration_v2.yaml
```

Validate only the maps and protocol with:

```bash
python train.py --config configs/confirmatory.yaml --validate-only
```

Run the preregistered matrix without changing its configuration after viewing
outcomes:

```bash
python train.py --config configs/confirmatory.yaml
```

For the remote parallel run, open **Actions → Confirmatory 40-seed experiment →
Run workflow**. GitHub executes one matched seed per job, with up to 20 jobs in
parallel. Each seed artifact is saved independently, so a failed seed can be
retried without repeating successful seeds. After all 40 jobs finish, the merge
job checks all 240 variant--seed policies, raw episode counts, checkpoints,
maps, and six canonical seed-0 rollout GIFs before publishing the downloadable
`confirmatory-v2-complete` artifact.

Shard jobs use `--defer-analysis`; their one-seed statistics are intentionally
not treated as evidence. `scripts/merge_confirmatory_shards.py` computes the
declared paired tests and interaction only after the complete 40-seed set has
passed validation.

### Generated evidence

After training, `train.py` evaluates each agent stochastically on validation
and test maps and also runs the secondary greedy test. Exact episode telemetry,
per-seed records, aggregate tables, and confirmatory tests are written
separately:

* `results/training_runs.csv`
* `results/training_episodes.csv`
* `results/evaluation_episodes.csv`
* `results/validation_runs.csv`, `test_runs.csv`, and `greedy_test_runs.csv`
* `results/confirmatory_tests.csv`
* `results/interaction_tests.csv`
* `results/confirmatory_decision.yaml`
* `results/calibration_decision.yaml`
* `results/protocol_manifest.yaml`
* `results/result_inventory.yaml`
* `results/*_summary.csv` and matching HTML tables

Training CSVs label curriculum-horizon completion as `Curriculum Success` and
record both the current `Training Horizon` and fixed
`Target Evaluation Horizon`. Only validation/test `Success` is full 100-step
survival and eligible for the primary claim.

```bash
python train.py --config configs/confirmatory.yaml
# CSV and HTML tables are written to the `results/` folder
```

Use `--stat-test` to choose the comparison shown in the descriptive aggregate
tables. Available options are `paired`, `welch`, `mannwhitney` and `anova`. The
confirmatory decision does not use this option: it always applies the declared
paired, Holm-corrected pure-survival tests in `confirmatory_tests.csv`.

## Components
* **PPO** – The main reinforcement learning algorithm used to learn policies from environment interaction.
* **ICM** – Adds intrinsic rewards based on prediction error of the agent's dynamics model to promote exploring unseen states.
* **RND** – Provides exploration bonuses by comparing a fixed random network with a trained predictor network.
* **Planner** – A one-step heuristic scores safe neighboring cells as `cost_weight * cost + risk_weight * risk + revisit_penalty`. PPO always executes its own sampled action; agreement with the advisory recommendation earns a decaying learning bonus.
* **Safety mask** – Every variant uses the same mask derived from the policy observation to exclude out-of-bounds moves and currently visible mines or enemies. The same mask is applied during action sampling and PPO updates.
* Planner and intrinsic bonuses affect learning returns but are excluded from the reported environment reward.

The demo notebook experiments with different combinations of these components to evaluate their effect on success rate and exploration.

## Environment features
The grid world includes optional *dynamic risk* and *dynamic cost* modes. When
enabled, hazard locations and traversal costs change over time. The default
exploratory configuration gives a `survival_reward` of `0.05` per step. The
confirmatory configuration uses `0.5` plus a terminal survival bonus of `5.0`
to align learning feedback with the pure-survival endpoint. Training,
validation, and held-out test maps can be exported with
`export_benchmark_maps`; training rotates across only the first split. The
environment's `render()` method returns RGB frames so that
`render_episode_video` can produce GIFs of agent behavior.

## Success metric
An episode is marked as a **success** only when the agent survives for all
`max_steps` without hitting a mine or colliding with an enemy. Training logs store
these binary flags and plots display the running success rate next to the reward
curve. Result tables also report average success across seeds so improvements in
reward cannot mask agents that simply die early.

## Running Experiments
Train all models from a configuration file:
```bash
python train.py --config configs/default.yaml
```
Checkpoints are saved under `checkpoints/` and tables under `results/`. Videos
are opt-in with `--render-videos`; plots are opt-in with `--plot-dir figures/`.
Hyperparameters can be edited in YAML or overridden on the command line.

Specify `--initial-beta` and `--final-beta` to linearly decay the curiosity
weight. The value decreases until two thirds of the episodes have completed,
then stays at the final level. For example:

```bash
python train.py --initial-beta 0.2 --final-beta 0.05
```

To run only the baseline and ICM comparison:

```bash
python train.py --variants ppo icm --num-seeds 5
```

To run the complete matched five-seed matrix:

```bash
python train.py --config configs/default.yaml --seeds 0 1 2 3 4
```

## Running Tests
Execute the unit tests with:
```bash
pytest -q
```
The full suite runs in well under a minute on a CPU.

## Reproducing Our Results
The provided Dockerfile allows you to recreate the exact environment used for
our experiments. Run the following commands:

```bash
git clone <repo-url>
cd WarzoneRobo
docker build -t warzonerobo .
docker run --rm warzonerobo \
    python train.py --config configs/default.yaml --num-seeds 5
```

Checkpoints are saved under `checkpoints/` and benchmark tables under
`results/` within the repository.
